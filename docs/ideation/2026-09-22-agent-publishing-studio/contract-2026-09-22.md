## Problem Statement

Birdcar needs a personal editorial power tool, not an autonomous content factory. Nick supplies the perspective and makes editorial decisions; agents develop the opportunity, ask questions, retrieve evidence, organize arguments, draft, review and prepare a release. The present application has no Admin UI or persistent publishing workflow: its Admin index is a permission-gated empty response and its ten-essay archive is read from Markdown files.

The first Admin surface must make the work approachable: a Flux Composer accepts a simple idea, an Ideas/Active writing dashboard separates the backlog from deliberate work, and a quiet manuscript editor carries prose and meaningful content blocks. Existing authorization, public-route boundaries and offer truth are foundations to reuse, not reasons to preserve the file-backed publishing architecture.

The business outcome is qualified service inquiries from relevant owners and operational leaders. Articles should help them recognize a problem, trust Nick's judgment, and understand when the pitch-free Walkthrough is useful. Neither traffic nor this implementation proves attribution or lead quality. No productivity baseline or model-quality benchmark has been established.

## Goals

1. Deliver the first usable Admin publishing workspace: submit an idea, develop it with agents, make the three human decisions, edit and review the manuscript, then publish or schedule an exact approved release without leaving the application.
2. Make every essay in the initial ten-article archive editable in the CMS while preserving its public prose, title, original date, URL, links, chart data and diagram meaning; keep original source files intact as migration evidence.
3. Keep Nick in control: agents advance only within an authorized stage, changes to human prose remain proposals, stale work cannot overwrite newer work, and a published release stays live while a replacement is developed.
4. Bound automatic work to a $5 allowance per publishing attempt, including model calls, research tools and retries; permit one three-lens review batch and one affected-area recheck before further work requires a deliberate human restart or allowance increase.
5. Complete a three-piece pilot covering an opinion-led piece, a practical explanation and an evidence-heavy article, with Nick approving voice and reader usefulness, all material factual/publication blockers resolved, and editing time, retained prose and actual spending recorded.

## Scope Boundaries

### In Scope

- First Admin shell and usable sign-in path, reusing Fortify, standard Admin routes, existing global identity and domain-local permission catalogs; Flux UI Pro with Inter. — The repository currently has no usable Admin UI. Publishing must have real authenticated entry and action-level authorization, including an explicit operator procedure to provision Nick's confirmed existing account with the catalog-defined Admin and publishing roles, without building a general administration suite.
- Flux Composer idea entry with Develop idea and Save for later; Ideas/Active writing dashboard, attention indicators and a separate published archive. — Nick explicitly selected this composition and clarified that submitting the simple idea should initiate agent-assisted development.
- One Flux rich-text manuscript editor with Markdown shortcuts, custom semantic notes/callouts/charts/diagrams, contextual block controls and a real public-article preview. — Nick approved this approach after a disposable prototype proved representative block edits and exact structured-document persistence across a full browser reload.
- Persistent editorial state, working revisions, save/conflict handling, protected human passages, explicit alternatives and immutable approved/live releases. — Agents, delayed jobs and human edits must not silently replace one another or publish unapproved material.
- Full migration of the original archive into editable CMS records, preserving original files as evidence and all public content identities and meaning. — Nick rejected a read-only legacy archive and on-demand migration; the first release must edit the whole archive.
- Agent-assisted interview/brief, human angle approval, live public-source research and challenge, narrative/outline and visual planning, human plan approval, and drafting from approved context. — The first useful release must complete the editorial journey, not ship a manual editor awaiting its intelligence.
- Small explicit editorial roles using OpenRouter, relevant voice examples separate from business truth and evidence, usage accounting, a $5 per-attempt allowance and bounded retry/pause behavior. — The tool must preserve authorship and control costs without a generic agent platform, model registry or automatically learned voice profile.
- Three same-revision review lenses, reconciled passage-specific proposals, explicit human dispositions, one targeted recheck, and publication-blocking factual/safety findings distinct from advisory style/discovery suggestions. — This is the approved review authority and stopping rule; model agreement is not proof and reviewers cannot independently overwrite prose.
- Purposeful structured visuals, release metadata/link/asset checks, exact-release approval, publish/schedule, and safe replacement of public Writing/RSS/sitemap content. — A usable publishing product must deliver the approved release, not stop at generating a draft. New diagrams use editable source plus preview rather than a visual drawing application.
- Owner-reviewed three-piece pilot and explicit acceptance gate, plus focused automated regressions and rendered archive/desktop/mobile review. — Passing tests does not establish voice fidelity, editorial usefulness or a usable writing interaction; no existing performance baseline is invented.

### Out of Scope

- Automated opportunity discovery and search-demand monitoring — Deferred after the owner-initiated publishing path is useful.
- Generated illustrations, automatic screenshot capture and a general media-management suite — Deferred capabilities; the first release focuses on supported structured editorial content and faithful existing assets.
- Email/social derivative generation and automated distribution — Nick selected a first release ending at publish/schedule.
- Outcome-driven topic recommendations, attribution dashboards and automatic voice learning — Deferred; pilot observations do not justify a learning platform or silent updates to editorial guidance.
- Admin MCP access and Customer MCP changes — The domain rules remain transport-neutral, but MCP is a later interface rather than a second first-release workflow.
- Multi-author collaboration, customer-tenant publishing and roles/permissions management UI — This is Nick's personal internal publishing tool; reuse authorization foundations without expanding the customer application.
- Visual diagram-design canvas, arbitrary editor plugins and arbitrary executable content — The approved approach is focused structured blocks and editable diagram source, not an extensible design application.
- Mandatory ZDR-only routing or a confidentiality/compliance administration subsystem — Nick says his work generally is not confidential and his contract will disclose AI use; no ZDR mandate is required. Publication rights still require independent judgment.
- Public marketing redesign, changed offers or changed archive prose — The public visual system and PRODUCT.md offer/proof boundaries remain authoritative.
- Unapproved dependency installation, paid evaluation calls or production deployment — Prototype dependency approval was temporary-sandbox-only. Production dependencies, credentials, real paid pilot execution and rollout require explicit authorization; no deployment is implied by this planning contract.

### Future Considerations

- Outcome-informed recommendations and owner-approved reusable voice/editorial learning.
- A separate Admin MCP interface reusing the same capabilities and transition rules.

## Decisions Considered and Rejected

- **Require separate angle, plan and exact-release approval for new pieces.** — rejected: Combining brief/outline into a single early approval gate.. Nick explicitly preferred control before both research effort and full drafting.
- **Plan the editorial process together with the first Admin dashboard and writing workspace.** — rejected: Ending this project at a process-only design document.. Nick expanded the initial gist boundary to include the first Admin UI, using Flux UI Pro and existing permissions.
- **Deliver an assisted end-to-end first release while deferring discovery automation, generated images, distribution, learning and MCP.** — rejected: The entire long-term vision at once, or a manual workspace with agents added later.. Nick selected the working editorial journey as the minimum useful product.
- **Use Ideas plus Active writing on the landing dashboard, with Published separate.** — rejected: Ideas plus Published as the primary split, or a decisions-first landing dashboard.. Nick selected a creation-focused workspace rather than leading with past output or a queue of administrative decisions.
- **Agents advance within the authorized stage and stop at human decisions, missing input and budget limits.** — rejected: Requiring a separate instruction or estimate approval for every agent activity.. Nick wants agents to start and advance useful work, not merely expose a set of manual AI buttons.
- **Use rich text with Markdown shortcuts for the manuscript.** — rejected: Markdown-source editing or interchangeable rich-text/Markdown editing modes.. Nick selected a quiet rendered writing surface; source-format round trips are not a product requirement.
- **Make the entire existing essay archive editable in the first release.** — rejected: Keeping legacy essays read-only or importing them only when individually revised.. Nick explicitly requires one CMS for old and new writing, with public fidelity preserved.
- **Run one three-lens batch and one affected-area recheck after accepted revisions.** — rejected: Two automatic revision cycles or recurring manual selection of every review.. The chosen default provides useful specialist feedback without an endless refinement loop.
- **Use a $5 automatic allowance per publishing attempt, spanning autosaves, generated revisions and retries.** — rejected: A $2 allowance or approval of every stage estimate.. Nick chose more room for meaningful research/escalation, while retaining an explicit stop and top-up decision.
- **Use a three-piece editorial pilot without an invented manual-work baseline.** — rejected: A single-piece acceptance pilot or an unmeasured time-savings promise.. Nick selected representative opinion, practical and evidence-heavy writing with measured observations and his own editorial judgment.
- **Use structured editorial blocks and source-based diagram authoring.** — rejected: Read-only figures or a full point-and-click diagram/chart design application.. Nick wants content to remain editable without making the CMS a general-purpose visual-design tool.
- **Material factual, invented-detail, confidentiality/rights and release-integrity issues block publication; style/discovery suggestions are advisory.** — rejected: Blanket editorial overrides for unresolved factual/rights issues, or requiring every advisory finding to be cleared.. Flags can be resolved by evidence, revision/removal or a reasoned false-positive disposition; reviewers advise rather than acquire editorial veto authority.
- **Keep AI processing and publication permission distinct, without requiring ZDR-only providers.** — rejected: Mandatory zero-retention provider routes for this personal publishing workflow.. Nick clarified that he does not generally handle confidential material and will disclose AI use contractually. An explicitly marked private source still needs deliberate processing consent and separate permission to disclose its contents.
- **Use documented Flux custom Tiptap extensions for one continuous manuscript editor, with contextual block controls.** — rejected: Assuming stock Flux preserves custom figures, or splitting the manuscript into separate prose editors solely to avoid extensions.. Boost's Flux 2 documentation confirms registerExtensions/init support. The 2026-09-22 disposable spike using installed Flux 2.19 and temporary Tiptap 2.11.7 retained two notes/callouts, chart data, a diagram and a link after edits and full browser reload; stock Flux dropped the figure nodes. It also exposed the need to isolate embedded-figure whitespace/typography. The temporary sandbox is evidence, not a runtime dependency or production implementation.
- **Use Flux Composer for initial idea entry; submitting Develop idea is explicit authorization to start the interview/brief, while Save for later is passive.** — rejected: Using the manuscript editor or a large article form as the initial idea input.. Nick clarified that he is logging a simple idea and letting an agent start a process. This preserves deliberate initiation without making capture cumbersome.
- **Separate automated safety checks from owner editorial/usability acceptance and later business outcomes.** — rejected: Treating green tests as voice approval or requiring a speculative conversion lift before launch.. Nick explicitly accepted the proposed acceptance checks; existing ideation learnings also warn that markup/build checks do not prove rendered behavior or human judgment.
- **Include an explicit owner-account provisioning prerequisite using authorization:sync and domain-local role assignments before the real Admin pilot.** — rejected: Assuming that installing authorization or seeding a User already grants Nick Admin and publishing access.. The hidden-dependency critic verified that the repository has no owner-role provisioning path. The implementation spec must identify an owner-confirmed existing account, require authorization for privileged assignments, assign roles rather than direct permissions, and never grant access from boot or migrations.
- **Mechanically compare original archive sources with the pinned pre-project Git baseline in addition to imported/rendered parity tests.** — rejected: Relying on public-content parity tests, or a clean working-tree diff alone, to prove the original source files were not rewritten.. The success-criteria critic exposed missing source-preservation coverage. Comparing against commit 72f7d8ad8521573cb224022c902447f9ca4c4351 detects source changes even after they have been committed.
- **Fail acceptance on skipped or incomplete Publishing tests using supported Pest runner flags.** — rejected: Assuming a normal green test-run exit code guarantees that all Publishing tests actually ran.. The success-criteria critic noted that skipped tests may otherwise pass; the installed runner confirms --fail-on-skipped and --fail-on-incomplete support.
- **Register Admin application routes explicitly in routes/web.php; reserve Folio for the marketing site.** — rejected: Using file-based Folio routing for the authenticated publishing application.. Nick explicitly reinforced this boundary after contract approval; it also matches the existing committed application-routing rule. Livewire components do not imply Folio routes.
- **Build a shared Admin shell and explicit module route/navigation boundaries, with publishing as its first module.** — rejected: Coupling the whole Admin layout and navigation to publishing, or prebuilding a generic module/plugin framework.. Nick expects substantial future Admin functionality. Reusable Flux/Inter layout, navigation and feedback patterns earn their place now; future module features, dynamic registries and permission-management UI remain out of scope.
- **Use Tiptap-compatible canonical JSON with server-side typed rendering, and restricted static SVG source for new diagrams.** — rejected: A parallel incompatible document AST, HTML as authoritative persistence, or additional diagram-rendering infrastructure.. Spec integration review aligned server node names/attrs with the approved editor and retained source-plus-preview authoring without a new drawing or runtime dependency. Original prose and figures remain protected by independent migration parity checks.
- **Implement OpenRouter through Laravel HTTP, using an explicit Exa web plugin, stored retrieved highlights and safe public fetch where supporting text is absent.** — rejected: Adding an AI SDK, implicit search-engine/provider fallback, or treating citation URLs alone as supporting evidence.. Current official OpenRouter documentation supplies a concrete one-vendor integration. Search and model charges remain inside pre-call reservations; uncertain prices/outcomes pause. Model/provider choices and paid calls stay owner-controlled execution inputs.
