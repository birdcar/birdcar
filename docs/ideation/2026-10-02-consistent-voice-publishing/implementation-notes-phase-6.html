Implementation Notes — Phase 6

Consistent Voice Publishing · 2026-10-12 · Distribution kit and sibling pieces

Kit document — where the kit fields live

Context
The File Changes row says LintTarget maps kit payloads to blocks; the Data Model says the document holds one paragraph per field or post and the metadata holds subject, preview and first_comment.
Decision
Every field (LinkedIn text and first comment, each Bluesky post, email subject, preview and body) is one paragraph in the document, and nothing is copied into metadata. Each block id is derived from its role (blk_ plus 16 hex of sha256('kit:<kind>:<role>')) by the new App\Services\Publishing\KitDocument, so LintTarget, the repair agent and the copy-out all find a field by id. A line break is a hard break; URLs stay plain text so a copied field keeps them.
Alternative
Subject, preview and first comment in metadata: their lint hits would have no block id, so the repair loop could never patch them and Accept fix could not apply. Storing the text in both places would drift on edit.

Kit lint context — flagship URL and target phrase

Context
linkedin-length needs the flagship's target query and the link rules need its canonical URL; LintRevision::hits builds a target only from the revision.
Decision
SpawnDistributionKit freezes flagship_article_id, flagship_release_id, canonical_url (built the way the sitemap builds it, with MarketingSite) and target_query into the kit attempt's brief, and a restart updates them. LintRevision::hits passes that brief to an optional LintTarget context, so the save-time lint, the post-draft lint and kit approval all see the same context. A null target query skips the target-phrase half of linkedin-length.
Alternative
Reading the flagship live at lint time: hit hashes (and so overrides) would change whenever the flagship changed, outside the kit's own approval.

Kit rules — repair and double hits

Context
The scout map flagged rules a single block patch might not fix (numbering, splitting a post, a link in two places).
Decision
Every kit hit points at the one block where one patch fixes it, and its message carries the exact fix ("Number this post 2/3 at its start.", "Link the post once in the last post: URL", "Remove the link to the post here"). So none is added to UNREPAIRABLE_RULES, and lint_repair keeps its rubric files: one bullet in roles/lint-repairer.md tells the repairer to follow a distribution hit's message. A LinkedIn piece with no link in its first comment gets both linkedin-link-in-comment and kit-links-post, as the spec table defines both; one patch clears both.
Alternative
Adding voice/kit-rules.md to lint_repair (every blog repair would carry LinkedIn rules), or marking the cross-block kit rules unrepairable (owners would fix mechanics the repairer can do).

Kit rules — counting

Context
Bluesky counts graphemes; URLs contain dots and slashes; the target phrase rarely appears verbatim with the same punctuation.
Decision
Lengths count Unicode code points (mb_strlen), like the packaging panel; the canon bans emoji, so this matches Bluesky for any text a kit may hold. URLs are found as bare text (scheme, www. or domain plus path) and as link marks, and two URLs name the same page ignoring scheme, www., case, a trailing slash, query and fragment, so a tracked link to the post still counts. Sentences end at . ? ! followed by space or end, with URLs set aside first. The target phrase matches ignoring case and punctuation within the first 210 characters. Hashtags are # at a word start followed by a letter, so #choose-a-time in a URL and #1 never count.
Alternative
grapheme_strlen (depends on intl, and identical for emoji-free text).

Lint applicability

Context
The spec says body rules apply to every kind and heading rules and walkthrough-link apply to blog posts only; it does not mention the Phase 4 metadata rules, BoldLimit or InlineHeaderList.
Decision
VoiceRule::appliesTo now returns true. A new AppliesToBlogPosts trait narrows the heading rules, walkthrough-link and all five metadata rules back to blog posts. BoldLimit and InlineHeaderList apply to kits (harmless on plain paragraphs). exclamation-limit allows none in a kit piece, as voice/mechanical-rules.md already says. The Drafter's document description now lists only the rules that apply to blog posts (VoiceLinter::ruleIdsFor).
Alternative
Leaving the metadata rules on every kind: kit revisions carry no packaging metadata, so they could only ever be noise.

Kit drafting — paused agents and owner edits

Context
Spec: pieces spawn and drafts wait for unpause. Restarting an unapproved kit on a new release could overwrite owner edits.
Decision
Spawn always creates the pieces and a Pending draft_kit (dispatched only when unpaused; publishing:recover-activities runs it later), the same as other started work. A kit draft lands only when the working revision was written by an agent (or there is none); otherwise it is stored as a proposal and the kit panel offers "Replace my text with this draft" (SpawnDistributionKit::useDraft, which lints and queues review). A restart moves the attempt to a new review cycle, stales its pending, paused, failed and awaiting work, and RunEditorialActivity stales any running kit work whose frozen flagship release no longer matches the attempt brief.
Alternative
Creating no activity while paused, as ApprovePublishingStage does for research and drafts; the spec wording favours drafts that wait.

Kit review and approval

Context
Spec: claim_outside_manifest blocks, register is advisory; channel severity, which review counts and how findings are decided were open.
Decision
The validator sets severity from the kind: claim_outside_manifest is always blocking, register and channel always advisory (LLM style findings stay advisory). Kit findings cite no evidence; a source id fails the activity, and the rubric says to name the manifest statement in rationale. Kit findings are decided at once (ApprovePublishingStage::decideKitFinding; a reason is required to keep the text or call it a false positive), because kit review has no finish step. Kit approval requires a completed review_kit in the current cycle, no lint hit without a reasoned override on the current revision, and no undecided blocking kit finding; its hash covers the text, flagship release, lint state and finding decisions. A save after approval invalidates it and moves an approved piece back to in review, so Phase 7's "Ready to post" column stays true.
Alternative
Requiring a fresh kit review after every owner edit: a paid review per typo fix, while lint re-runs on the exact revision anyway and the owner reads the piece before approving.

Mark posted — the flagship check

Context
Spec: flagship published_release_id not null and flagship attempt stage published.
Decision
MarkKitPiecePosted checks the flagship's published release is live (status published, published_at set) and that release's own attempt reached Published, not the flagship's current attempt. develop() starts a new current attempt after publication, which would otherwise refuse posting forever. It also requires an active Kit approval on the working revision, refuses a second mark, and accepts only https posted URLs of at most 2,048 characters (never fetched).
Alternative
The literal current-attempt check (fails after any post-publication develop).

Which posts spawn a kit, and the fallback

Context
The scout asked whether siblings and archive essays spawn kits, and what happens if spawning fails after the approval commits.
Decision
Every parentless blog post that is not an archive import spawns its own kit on release approval, siblings included (the blog channel says each finished post yields a kit). Spawning runs after the approval transaction; a failure is reported, never rolled into the approval, and the post's release tab lists its kit with a "Create distribution kit" button when pieces are missing. Kit pieces belong to the post's author.
Alternative
Kits for the flagship only (a sibling would ship without one), or spawning inside the approval transaction (a kit error would undo the approval).

Canon — the short-form exemplar

Context
Spec: use the register's LinkedIn-length line and CTA examples; kit-no-walkthrough-cta forbids the CTA in kit pieces.
Decision
exemplars/short-form.md keeps the LinkedIn-length line and three short register lines, and says the Walkthrough invitation is deliberately missing because the post carries it. The file is listed only in draft_kit, never in the exemplar manifest, so the blog drafter's exemplars are unchanged. roles.json gives draft_kit and review_kit the files the spec names, and the interviewer rubric gains a Sibling posts section (and reads the owner's optional note as sibling_note).
Alternative
Including the CTA labelled "do not copy": a short-form exemplar invites imitation.

Spec premise — EditorialInputContractTest

Context
The spec says the input contract test extends itself to the new kinds.
Decision
It does not: its dataset, response match, prerequisites and exact-case list are explicit. They now cover draft_kit and review_kit, with a kit piece spawned from a directly published flagship release, plus tests that kit inputs carry the piece kind, flagship text, URL, target phrase and claim manifest, and that a caller cannot forge them.
Alternative
None; this is a correction of a test claim, not a design choice.

Workspace — the kit panel

Context
Spec: a compact kit panel with no develop or plan tabs.
Decision
Kit pieces render partials/kit.blade.php instead of the tab group: each field with a character count and an Alpine copy button, an edit form (Bluesky posts can be added and removed), the shared voice-rules section (extracted to partials/voice-rules.blade.php so the blog layout renders the same markup), kit review findings, approval with the reasons it is blocked, and Mark posted with its refusal reason. Blog posts gain "New post from this idea" in the header and a distribution kit list in the release tab. The dashboard and Admin home still list kit pieces as ordinary work in progress; Phase 7 owns the board.
Alternative
Reusing the Tiptap editor for kit fields: it would let the owner add blocks that have no kit role.

Codebase surprise — Livewire hydrate hooks

Context
A private workspace method named hydrateKitFields failed with "Method ... does not exist".
Decision
Livewire treats hydrate{Property} as a lifecycle hook for the kitFields property, so the method is named loadKitFields.
Alternative
None.
