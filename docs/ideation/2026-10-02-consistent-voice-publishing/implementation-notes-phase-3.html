Implementation Notes — Phase 3

Consistent Voice Publishing · 2026-10-12 · Deterministic voice lint

Lint rules — canon over spec: every rule that departs from the spec's detection table

Context
The spec's detection table differs from the statements the Drafter is told in voice/mechanical-rules.md; the two-way test compares ids only. The Drafter is held to the canon, so where the two disagree the linter follows the canon. This entry is the one place the acceptance review of the word lists should read.
Decision
Word lists are the union of both, minus items that need judgment (bare "stack" and "scale" as a hype verb stay with the voice reviewer). Per rule, against the spec table: filler-phrases adds "it is important to note"; chatbot-artifacts adds "here is an overview of", "while details are limited", "based on available information"; stock-openers adds "In this article", "Let's dive in", "In conclusion", "Ultimately,"; label-headings adds "bottom line", "key takeaways"; corporate-we adds "ourselves"; experience-claim adds "over fifteen years"; bold-limit allows one bold span per H2 section instead of two per piece (see its own entry); exclamation-limit also flags every "!" in a heading, the title and the description; sentence-case-headings also exempts "Nick", "I" and its contractions, and words inside straight quotes. Matching is exact on word boundaries, case-insensitive, with straight and curly apostrophes; inflections such as "leveraging" are not caught. "align with" fires both ai-vocabulary and corporate-vocabulary ("align"); the repairer fixes both in one patch. These are spec deviations. Owner: review the lists at acceptance, as the spec's failure-mode table suggests.
Alternative
Inflection matching (more recall, more false positives), or the spec lists alone (the Drafter would be told rules the linter does not enforce).

bold-limit — the canon's per-section reading, not the spec's per-piece count

Context
The spec says more than two bold spans per piece; the canon tells the Drafter "use bold at most once per H2 section".
Decision
At most one bold span per H2 section (text before the first H2 is a section); one hit per extra span. Enforcing the spec's count would repair or block drafts that follow the rule the Drafter was given. This is a spec deviation.
Alternative
The spec's more-than-two-per-piece count.

exclamation-limit, heading-order, walkthrough-link — readings

Context
The canon also bans "!" in headings, titles and descriptions; a level-1 heading cannot be saved; the canon puts the link "in the closing invitation paragraph".
Decision
Every "!" in a heading, title or description is a hit, and the body allows one. heading-order flags a level-1 heading or a skipped level, so in practice an H3 before any H2. walkthrough-link follows the spec: exactly one /walkthrough link (relative or birdcar.dev, with or without www, slash, query or fragment) after the final H2, or in the last three blocks when there is no H2. With no link, the hit points at the last block so a repair can add the invitation link; misplaced and extra links are hit at their own block.
Alternative
Locating the "closing invitation paragraph" by its wording, which is not deterministic.

LintTarget — what counts as a block

Context
The spec lists block fields but not attribute text or legacy text.
Decision
One block per paragraph and heading, plus note/callout titles and chart/diagram captions as their own blocks (all body rules apply to that visible text). Code blocks and code-marked text are skipped, with a space left so words do not fuse. Protection and blockquote flags are inherited from ancestors. Adjacent bold nodes and same-href link nodes merge. Blocks without an id (only possible for revisions written around WriteArticle) fall back to their JSON path. Metadata gets the character rules only (em dash, curly quotes, emoji, excluded names, unresolved markers, "!"), never sentence case; Phase 4 owns title rules.
Alternative
Ignoring attribute text, which would let an em dash in a caption reach release.

LintHit — excerpts and hash collisions

Context
The hash is sha256(rule | block | excerpt); repeated excerpts in one block collide.
Decision
Word and phrase rules use the matched words as the excerpt, so an override survives edits elsewhere in the block. Character rules (em dash, curly quotes, emoji, "!") use about two words either side, so two dashes in one block are two hits. A repeat of the same rule, location and excerpt is numbered in reading order (LintHit::$occurrence), and occurrences after the first add their number to the hash, so each is its own finding and needs its own override; an override recorded on one "leverage" no longer clears a second "leverage" added to that block later. The first occurrence keeps the plain hash. Known trade-off: removing an earlier occurrence renumbers the later ones, so an override can move to, or fall off, a neighbouring identical hit; the failure that matters for release (a new occurrence passing silently) is closed. Metadata hits hash with $.metadata.{field} in place of the block id. Changed after review cycle 1, which flagged the earlier merge of identical hits.
Alternative
Merging identical hits into one finding (the cycle-1 behaviour: one override covered every occurrence in the block), or a wider excerpt for word rules (overrides would break on nearby edits).

Repair loop — what is repairable, and when the loop stops

Context
The spec sends every hit to repair; the Drafter is told to write [NEED: proof] markers.
Decision
Unresolved markers and metadata hits are never sent to the repairer (fixing them would mean inventing proof or there is no block to patch); they are stored as findings at the end of the step. Hits are grouped by block in the frozen input (blocks[] carries each node and its subtree hash for the model to echo), and the output allows one patch per block. The loop stops at two completed repairs per review cycle, or early when a pass applied nothing.
Alternative
Sending markers to the repairer, or one patch per hit (later patches would fail their expected hash and burn the cap).

Repair — "agent-authored" is tracked per block, not by the latest agent revision

Context
The spec defines agent-authored as "the block's subtree hash equals its hash in the most recent agent-initial or agent-repair revision".
Decision
A repair revision carries owner-edited blocks forward unchanged, so the literal definition (compare against the whole latest agent revision) would let the second repair pass rewrite owner text. Instead each block keeps the hash an agent last wrote for it in this attempt: every block of the applied draft, then each block a completed repair changed, later writes replacing earlier ones. A block is agent-authored only when its current hash equals that latest write, so an owner who restores text an agent wrote before its latest pass is treated as the author. Protected blocks (including through an ancestor) are never patched. Unapplied patches are kept on the repair's proposal and attached to the matching finding when the step ends, if the block still matches. This is a spec deviation, narrowed after review cycle 1 (which flagged that any earlier agent write counted).
Alternative
The spec's literal definition (the owner-edited workflow test fails under it), or any agent write in the attempt (an owner restoring earlier agent text got auto-repaired).

Repair failures — unusable output ends the step, provider failures do not

Context
The error table says invalid repair output fails the activity and the lenses still queue; nothing hooked failures before.
Decision
When the provider answered but the output could not be used (validation or apply error), the repair fails with that reason and the step finishes: findings are stored, the lenses queue on the repair's revision, and the repair is then marked Stale with its reason plus "Review started without this repair." Stale work cannot be retried (so no repair revision lands under the running lens batch) and does not show "Skip repair and review". When the step cannot finish (attempt blocked, revision moved), the repair stays Failed or Paused for the owner. When the request itself failed, the repair pauses or fails with no lenses, and the owner retries or uses "Skip repair and review". The Stale marking was added after review cycle 1.
Alternative
Leaving every failure to the owner, which stalls review after a bad model answer.

Protected passages — a fix survives the unlock that makes it acceptable

Context
A patch for a protected block can only be accepted after the owner unlocks it, but unlocking saves a new revision whose block hash differs (only attrs.protected changed), and the repair output had to keep protected: true in the replacement. Review cycle 1 found "Accept fix" was a dead end for protected hits.
Decision
When LintRevision carries a patch to a new revision, it accepts a block that is unchanged or differs only in its own attrs.protected, and rebases the patch: expected_hash becomes the block's current hash and the replacement's attrs.protected mirrors the block's current value. Unlock then "Accept fix" applies the fix and leaves the passage unlocked; any other change to the block still drops the patch. EditorialOutput still requires the repairer to keep the lock it was given.
Alternative
Normalizing protection everywhere in the subtree (a replacement would then overwrite a descendant's newer lock), or letting accept bypass the lock (breaks "agents never silently change protected prose").

Skip repair and review — added to the workspace

Context
The failure-modes table names the action, but File Changes does not.
Decision
LintRevision::skipRepair behind the workspace's skipVoiceRuleRepair (develop gate). It refuses while a repair is running, marks pending, paused and failed repairs in the cycle stale, stores findings on the current revision and queues the lenses. It shows only while a repair is waiting. After an owner edit the lenses still need a drafted or repaired revision, as the existing "Start three-lens review" button does.
Alternative
Letting skip start lenses on owner-edited revisions, which would change review eligibility beyond this phase.

Overrides — immediate, article-wide, part of the release hash

Context
decideFinding only buffers until finish review, but release reads the database.
Decision
"Override with reason" writes the false-positive disposition immediately (approve gate, trimmed non-empty reason). Release matches overrides by hit hash across the whole article, ignoring stale_at, cycle and attempt, and LintRevision copies an override (and a still-valid proposed patch) forward to the new revision's finding. The release input hash now includes each hit and its override reason, so changing an override stales a prepared release. Side effect at deploy: releases prepared before this change re-prepare once, because the hash shape changed.
Alternative
Scoping overrides to one attempt, which would force the owner to repeat them after a new attempt.
