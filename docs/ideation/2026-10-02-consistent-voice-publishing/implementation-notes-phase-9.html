Implementation Notes — Phase 9

Consistent Voice Publishing · 2026-10-12 · Drift trial harness and edit distance

Voice finding kinds — an enforced enum, not only a description

Context
The spec changes only the rubric and the VoiceReviewer kind description. A description alone lets the model return any string, but the trial's drift_flagged matches voice_drift exactly, and the contract's validator-to-schema audit expects every schema rule to be enforced.
Decision
ReviewVoice has its own schema arm: kind is a required enum of EditorialOutput::VOICE_FINDING_KINDS (voice_drift, clarity, framework, register), and the findings description defines each one the way roles/voice-reviewer.md does. EditorialOutput rejects any other kind through a helper shared with kit findings; the reviewer's severity stands. Facts and buyer findings are unchanged, so FactReviewer's description stays exactly "At most 25 findings.". ReviewRubricTest::reviewRubricFinding now sends kind: clarity, which the facts and buyer lenses accept as any string.
Alternative
Description only: a model that writes "voice" or "style" would never count as drift, and the stored kind would be free text.

Golden set — passages are linted without walkthrough-link, through one shared builder

Context
walkthrough-link hits the last block of any blog post with no /walkthrough link, which every 1-3 paragraph excerpt is. It would make every real passage "flagged" (failing G3's limit of 2) and fake catches on slopped passages whose last block is injected.
Decision
tests/Fixtures/Publishing/DriftGoldenSet.php (not in the spec's file list) loads and narrows passages.json, builds each passage document with stable blk_ ids from sha256('drift:<id>:<index>'), and lints it as a blog post with no metadata, minus EXCERPT_EXEMPT_RULES = ['walkthrough-link']. DriftFixtureTest and the paid trial both use it, so the free check and the paid run see the same manuscript and the same lint.
Alternative
Appending the same closing invitation to every passage: the reviewer would see one shared paragraph in all 20 manuscripts, and a voice_drift finding on it would flag a real passage.

Golden set — four slopped passages carry no mechanical tell, and each attempt records who caught it

Context
A slopped passage counts as caught when lint or the reviewer hits an injected block. If every slopped passage also carried a mechanical tell, lint alone could pass G3 even if the reviewer caught nothing, which contradicts the spec's "measures the VoiceReviewer and not only the linter".
Decision
Six slopped passages carry one mechanical tell (each a different rule: stock-openers, filler-phrases, negative-parallelism, ai-vocabulary, chatbot-artifacts, corporate-we) plus non-mechanical tells; four (slop-03, slop-05, slop-08, slop-10) carry only non-mechanical tells, so at least four catches must come from the reviewer. Each attempt also records caught_by_lint and caught_by_reviewer (extra keys the jq check ignores). DriftFixtureTest asserts that every lint hit on a slopped passage is exactly an injected mechanical tell on its block, so the records stay honest. Owner's call whether to shift that balance.
Alternative
A mechanical tell in every slopped passage: the gate would mostly measure the linter.

Golden set — passage choice, and the reviewer sees the originals in its own exemplars

Context
The spec asks for lint-clean passages without "10x", "kinda", profanity or practitioner-only jargon. The real passages come verbatim from the four canon essays and the site copy, and review_voice receives those texts in full as input.canon.exemplars.
Decision
Seven essay passages (two each from three essays, one from the fourth) and three site-copy passages, chosen without links, Markdown emphasis, "we/our", or developer jargon such as middleware, endpoints or refactoring; DriftFixtureTest asserts each real block appears verbatim in its source exemplar. For the owner: the real-flagged count is partly a recognition test, and each slopped variant sits next to its original in the reviewer's exemplars. This follows G3 ("canon or site-copy passages") and does not contradict the decision log.
Alternative
Passages from outside the exemplar canon: G3 names canon or site-copy passages.

Paid trial — one neutral brief and plan for every passage

Context
Retrieval needs query text (brief summary, target query, angle thesis, plan argument), and nothing should hint whether a passage is real or slopped. The rubric's framework-adherence section would report structural gaps on a 1-3 paragraph excerpt.
Decision
Every passage gets its own idea and piece but the same constant brief, idea text and human-written plan, with no post_type and no framework, so input.canon.framework is absent and the reviewer skips framework adherence. The angle is approved and a completed research row is created while agents are paused; the plan is approved unpaused, so retrieval runs and freezes exemplars for the Draft, which is force-completed without a paid request because the passage is the manuscript. The trial asserts all 20 reviews completed and leaves the G3 thresholds to the contract's jq check, which recomputes them from the attempts.
Alternative
A per-passage topic brief: it would need a field the spec's fixture shape does not have, and it would vary the context between real and slopped variants.

Paid trial — canon hash after Phase 8

Context
The trial runs migrate:fresh on birdcar_test. Once Phase 8 makes the snapshot read the active Admin canon version, the jq check's php artisan publishing:canon-hash runs against development and returns that version.
Decision
canon_hash comes from app(VoiceCanon::class)->snapshot()->version, the same source the command prints, and the trial's header comment states the limitation: the two match only while the active canon is the repository canon.
Alternative
Copying the development canon versions into the test database: not possible from an isolated run, and outside this phase.

Edit distance — autosave makes "the owner's next saved revision" a small number

Context
The editor autosaves after 250 ms idle, and every save is a revision. The first owner revision after an agent revision is usually the first burst of typing, and later owner saves have an owner parent, so they record nothing.
Decision
Implemented exactly as G6 and the spec say (the owner's next saved revision). Flag for the owner: most recorded distances will be a few words, not the owner's total edit. Changing the baseline (for example, measuring the latest agent revision against the current working revision in the command) is a contract change.
Alternative
Measuring to the latest owner revision or summing a run of owner saves: not what the contract records.

Edit distance — which saves measure, and how words are read

Context
The spec names agent-initial, agent-repair and agent-accepted. The legacy agent origin is still listed in the protected-block guard but nothing writes it. The spec does not say which text counts or how punctuation is treated.
Decision
ArticleRevision::AGENT_ORIGINS holds the three named origins only. WriteArticle::save dispatches RecordEditDistance after commit, inside the transaction after the revision is created, only for a human save whose parent has one of those origins, so mutation-id replays and rolled-back saves dispatch nothing. Words are lowercase runs of letters and digits (an inner straight or curly apostrophe keeps "it's" one word) from every text node plus note and callout titles and chart and diagram captions; blocks and hard breaks separate words, and a word split across marks stays one word. Punctuation-, case- and formatting-only edits measure 0. The distance trims the shared opening and closing words, then runs a two-row dynamic program over integer word ids; a full 4,000-word rewrite stays well under 16 MB in the test.
Alternative
Character-level distance, or counting formatting: the spec asks for word-level, and formatting is not the owner's prose.

Edit distance — the job never fails a save, and the guard needs the column loaded

Context
Tests run the queue synchronously, so a job exception would surface from WriteArticle::save (and workspace autosaves) after the revision committed. The spec says the guard permits setting the two columns once from null, only from the job.
Decision
The job returns early for a missing revision, a non-owner revision, a parent no agent wrote, or a distance already recorded; it writes with whereNull('agent_edit_distance')->update(...) on the revision it was queued for, so a second run is a no-op; any unexpected error is reported, not thrown. The model guard throws "An edit distance is recorded once and cannot be changed." when either column changes from a non-null value, or when a model that never loaded the column tries to set it. "Only from the job" is a convention stated in the docblocks.
Alternative
Letting the job throw: a measurement failure would read as a failed save to the owner.

Edit-distance command — one value per piece, plus every recorded distance

Context
The spec's shape has one edit_distance per piece, but a piece can record several (an initial draft edited by the owner, then an accepted proposal edited again).
Decision
edit_distance is the latest recorded distance, or null when none was recorded; each piece also lists distances: [{revision_id, baseline_revision_id, edit_distance}] in revision order. Every piece of the idea is listed (flagship, siblings and kit pieces) with its kind's enum value, so the owner picks the four the acceptance record needs. A missing or non-numeric idea prints an error and fails.
Alternative
Summing all distances: it would mix measurements against different agent baselines into one number.
