Implementation Notes — Phase 8

Consistent Voice Publishing · 2026-10-12 · Canon editor

VoiceCanonVersion — activation is the one permitted update

Context
The spec makes the model immutable ("updating and deleting throw") but also defines rollback as re-activating an older row, which sets its activated_at.
Decision
The updating guard throws unless the only dirty attributes are activated_at and updated_at; deleting always throws. Every other column is fixed at insert.
Alternative
A query-builder update that bypasses model events, so updating could throw unconditionally. Rejected because it hides the one mutation path instead of declaring it.

VoiceCanonVersion — activations order strictly, to the microsecond

Context
The active version is "the row with the most recent activated_at". At second precision, a save followed by a rollback in the same second ties, and the rollback could lose.
Decision
activated_at and the timestamps are timestamp(6), the model keeps microseconds ($dateFormat), and markActive() sets the later of now and the previous activation plus one microsecond. The scope orders by activated_at then id.
Alternative
A separate activation sequence column (not in the spec's data model), or ordering ties by id (wrong for a rollback to a lower id).

Locking — one Postgres advisory transaction lock

Context
Saves must reject a stale base, and the sync must not race a save, including the first sync into an empty table where there is no row to lock.
Decision
Save, activate and sync all take pg_advisory_xact_lock through VoiceCanonVersion::lockForChange() and re-read the active version under it. The unique hash still backs it up.
Alternative
lockForUpdate() on the active row, which cannot serialize two writers while the table is empty. The app is Postgres-only (pgvector), so the advisory lock is not a portability loss.

SaveVoiceCanonVersion — the first save records the repo baseline

Context
The spec does not say what a save does when no version exists yet (the deploy sync has not run in that environment).
Decision
The save runs the sync inside its transaction first, so the repo files become an active repo version and the Admin version is its child. Rollback to the repo baseline is then always possible, and the next deploy sync is a no-op.
Alternative
Refusing to edit until the sync has run, or saving an Admin version with no parent, which would leave no repo version to roll back to.

SaveVoiceCanonVersion — an edit identical to an older version is refused

Context
hash is unique, and the spec only rules out a version equal to the active one ("no empty versions").
Decision
An edit whose hash matches an earlier version is refused with "This edit matches version X. Activate it from the version history instead." Nothing is written.
Alternative
Silently activating the earlier version, which would drop the owner's note and authorship and turn a save into a rollback.

SaveVoiceCanonVersion — rule ids are checked against the rubric of the drafter that must pass them

Context
Spec step 3: every VoiceLinter::ruleIds() id appears in the draft rubric "(and kit ids in the draft_kit rubric)". Kit-only rules (for example linkedin-length) are not in the draft rubric, so a literal "every id in draft" check would reject the repo canon itself.
Decision
An id that lints blog posts (ruleIdsFor(BlogPost)) must be tagged in a draft rubric file; an id that lints any kit kind must be tagged in a draft_kit rubric file; an id that applies to both must be in both. Error messages name the rule, the role and its rubric files.
Alternative
Checking every id against the union of both rubrics, which would let a blog rule move out of the Drafter's rubric unnoticed.

SaveVoiceCanonVersion — "every referenced file" includes the framework catalog's files

Context
The spec lists roles.json files explicitly. StartEditorialActivity::structureCanon silently freezes nothing when a catalog template or framework file is missing.
Decision
Save validation also requires every post-type template and framework file named in frameworks/catalog.json, and builds the full snapshot (goals, exemplar manifest files, archive sources) through VoiceCanon::snapshotOf().
Alternative
Validating only roles.json, which would let a catalog edit quietly drop the chosen framework from every Drafter input.

SyncVoiceCanonFromRepo — "the previous repo version" is the newest repo row

Context
The auto-activation rule needs "the previous repo version". When the owner commits an Admin download, the next sync is a no-op and records nothing, so the table cannot know the repo then matched the Admin version.
Decision
A new repo version activates only when nothing is active or the active version is the most recently created repo version. Consequence for the owner: after committing an Admin download, the next repo change lands inactive and the editor shows the "repo baseline changed" notice; one click adopts it. It never overrides Admin edits.
Alternative
Adding a column to remember which version the repo last matched (outside the spec's data model), or treating any active version whose hash once equalled the repo hash as the previous repo version.

Editor — the repo-baseline notice and what it compares

Context
The spec asks for "The repo baseline changed" with a files-changed summary and an activate button, without defining when it clears.
Decision
The notice shows while the newest repo version is not active and has never been activated. It lists files changed, added and removed between the active version and that repo version. Activating it, or any later activation of it, clears the notice for good.
Alternative
Showing it whenever the active hash differs from the repo hash, which would nag after the owner deliberately rolled back to their own edit.

Editor — one file at a time, existing files only

Context
The spec says "edit one file at a time". Adding or deleting canon files is not mentioned.
Decision
The editor opens one existing file of the version it loaded, and a save changes that file. Switching files with unsaved changes asks first (Alpine $wire.$dirty). The save action itself accepts any complete file set and rejects paths that are not relative .md/.json paths, which keeps the download free of path traversal.
Alternative
A multi-file draft map, which the settings save bar cannot track as dirty once it lives server-side.

ActivateVoiceCanonVersion — rollback checks readability, not lint coverage

Context
Save validation is specified; activation validation is not.
Decision
Activation refuses a version that is already active or whose archive exemplar hashes no longer match the files on disk (the snapshot would throw). It does not re-run the lint-rule coverage check, so rolling back to a version older than a newly registered lint rule is allowed.
Alternative
Running full save validation on activation, which could block a rollback in exactly the moment the owner needs it.

VoiceCanon — no fallback when the table is missing

Context
Rollout: "revert; VoiceCanon falls back to repo files when the table is absent."
Decision
Read as describing the reverted code. snapshot() queries the table without a Schema::hasTable check, so an environment must run migrations before this code serves requests (Cloud runs them in the deploy commands). VoiceCanon::forget() was added so a save or activation in the same scope is visible to the next read.
Alternative
A hasTable check (one more query per request and job) or catching the missing-table error, which would abort an enclosing Postgres transaction such as StartEditorialActivity's.

Tests — the settings rail order changed

tests/Feature/Settings/SettingsShellTest.php pins the rail to Mail, Publishing, Profile, Security, Preferences.
Decision
Updated the expectation to include "Voice canon" after Publishing, matching the registry order in config/admin.php.
Alternative
