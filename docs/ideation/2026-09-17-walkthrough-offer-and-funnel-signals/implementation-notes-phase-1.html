Phase 1: Funnel instrumentation

Spec: spec-phase-1.md · Built 2026-09-17 · Headless, strict

What was built

  • posthog-js@1.433.10 added with bun add; bundled through resources/js/analytics.js, booted from data-posthog-token/data-posthog-host on <body>.
  • PostHogService::browserConfig() is the single read of enabled state for the layout.
  • Every booking control carries data-booking-cta="<placement>" via a new placement prop on booking-link; the assessment hero anchor is now the component with inline; the plain Cal.com link carries data-booking-fallback.
  • booking.js forwards Cal.com linkReady → booking_embed_opened and bookingSuccessfulV2 → booking_completed with only mode, booking_uid, event_type_id, start_time, status.
  • phpunit.xml pins POSTHOG_DISABLED=true, a blank token, and the US host, and sets failOnEmptyTestSuite="true".
  • tests/Feature/MarketingAnalyticsTest.php: five tests covering emission, the two omission paths, homepage placements, and the assessment hero and fallback markers.

Gap decisions

DecisionReason
isEnabled() not addedThe spec lists it, but nothing in the app, tests, contract, or later phases calls it, and browserConfig() returning null already communicates the state. The context map flagged it as unused and the owner's standing rule is to delete unused code. Add it in the phase that first needs it.
bun.lock tarball URLs normalised to ""This machine routes installs through the policy-managed WorkOS Socket Firewall registry, which made bun add rewrite all 300+ existing entries with socket-firewall.workos.dev URLs. The firewall config was left untouched (the install was scanned through it); only the lockfile's resolved URLs were reset to bun's default-registry form so the diff is the 25 lines for posthog-js and its dependencies. bun install --frozen-lockfile confirms the lockfile is consistent.
failOnEmptyTestSuite kept although Pest already failsPest 5.1.4 exits 1 on "No tests found." without the attribute. It is kept as the spec asks so a direct PHPUnit invocation behaves the same way.
Placement test split into homepage and assessment testsTwo requests, two subjects; each failure names the page at fault.
No describe() blockExisting marketing tests use flat test() calls; the file covers one flow.

Not done in headless mode

  • Dev-server checks against live PostHog (debug window, opt-out/opt-in, modal open count for linkReady, a real test booking). These need a browser and create real persons/events in the production PostHog project; they remain the spec's Open Items for the gate.
  • If linkReady proves to fire once per page rather than per modal open, switch the opened signal to bookerViewed.
