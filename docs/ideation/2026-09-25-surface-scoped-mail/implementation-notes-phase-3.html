Mail settings page — validation rules tightened to match the settings class

Context
The spec listed from_address: required|email, reply_to: nullable|email|max:254 and from_name: required|string|max:100.
Decision
Used email:filter for both addresses, added bail|string to the From address, string to reply-to, and not_regex:/[\r\n]/ to the name. Bare email is RFC validation and accepts owner@localhost, and the name rule accepts CR/LF; updateSender() rejects both, so those inputs would have passed validation, thrown in the save, been reported, and shown the misleading “Reload the page” message instead of a field error. A dataset row covers each.
Alternative
Keep the spec's rules literally and let updateSender() throw into the catch branch.

Mail settings page — key status treats an unset key as missing

Context
The spec's sketch says keyConfigured is mail.mailers.resend_{surface}.key !== '', but the key config has no default, so an unset key is null and would read as configured.
Decision
is_string($key) && $key !== ''. The missing-key test runs for both null and ''. The beforeEach pins both keys to '' because the local .env holds real keys.
Alternative
The literal !== '' comparison.

Mail settings page — feedback, errors and saved values scoped per surface

Context
The spec gives one Save per surface but a single ?string $feedback / $saveError, and Livewire's validate() replaces the whole error bag, so saving one surface would wipe the other surface's field errors while its invalid draft stayed on screen (and wire:dirty clears after any request).
Decision
Kept the spec's two string properties and added ?string $feedbackSurface so the success line, the “Nothing was saved” alert and the danger callout render in the section that was saved. save() validates only senders.{surface}.*, reads input from the validated subtree, and re-attaches the other surface's existing errors on both success and failure. Each section also shows a server-rendered “Saved:” line with the stored sender, so an unsaved draft can't be mistaken for the stored value.
Alternative
Keyed arrays for feedback and errors (changes the spec's property shapes), or accepting that one surface's save clears the other's errors.

Records — stale bundle and navigation text reconciled beyond the spec's file list

The spec lists .ai/rules/authorization.md but not docs/development-setup.md:137, docs/production-setup.md:91 (both name the two-role bundle), DESIGN.md:395 (“Only Home and authorized Publishing are present”) or the layout header label, which would have read “Home” on /mail.

The .impeccable surface brief is a design-review record and was left alone. The contract env grep still passes.

Leave the docs stale until a later phase.

Verification — authenticated browser check not run

Context
The spec asks for a Herd check of admin.birdcar.test/mail in light and dark after bun run build, and says to give the local account the new role via admin:invite or tinker.
Decision
Ran authorization:sync locally, built assets, and confirmed Herd serves the route (a guest gets 302 to /login). Did not change the owner's local account or send a real invitation from an unattended run, and a signed-in visual check needs the owner's credentials. Owner step: assign the role (e.g. php artisan tinker --execute 'App\Models\User::where("email", "YOU")->firstOrFail()->assignRole("mail.operator");'), then check the page in both themes.
Alternative
Re-run admin:invite for the owner's account, which sends real mail through the local catcher and issues a new reset token.
